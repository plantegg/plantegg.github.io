tcpdump 抓包卡顿分析

背景

从 192.168.104.1 上执行 ping 192.168.104.4 -c 1 ping 命令很快通了, 同时在ubuntu 机(192.168.104.4) 上抓包

在192.168.104.4 上的 tcpdump 要卡很久(几十秒)后才输出几十秒前抓到的包 :(，最一开始以为是自己通过 lima 虚拟化的 ubuntu 机器慢 or tcpdump 初始化慢导致的，但是发现等了几十秒后能看到几十秒前抓到的包，感觉有点诡异，所以分析了一下原因。

既然几十秒后能看到几十秒前的包，说明抓包正常，只是哪里卡了，所以用 strace 看看卡在了哪里。

于是在 /etc/hosts 添加 192.168.104.4 localhost 后不再对 192.168.104.4 进行解析，但是仍然会对对端的 IP 192.168.104.1 进行解析：

  • 上图最后一个绿线表示 tcpdump 抓到了 ping 包(ICMP 协议包)
  • \0011\003104\003168\003192 表示：192.168.104.1 ，\0011 前面的 \001 表示 1 位，1 表示 ip 地址值的最后一个 //把整个双引号内容丢给 GPT 会给你一个很好的解释

步骤 2

从上面两个图中的 connect 内核函数可以看到每次都把 ip 丢给了 127.0.0.53 这个特殊 IP 来解析，下面是 GPT 给出的解释，我试了下将 DNSStubListener=no(修改配置文件：/etc/systemd/resolved.conf 后执行 systemctl restart systemd-resolved） 后 tcpdump 完全不卡了：

systemd-resolved:

  1. systemd-resolved 是一个系统服务，负责为本地应用程序提供网络名称解析。
  2. 它作为一个本地 DNS 解析器和缓存，可以提高 DNS 查询的效率。
  3. systemd-resolved 支持多种 DNS 协议，如 DNSSEC、DNS over TLS 等。
  4. 它可以管理多个网络接口的 DNS 设置，适合复杂的网络环境。

DNSStubListener 参数:

  1. DNSStubListener 是 systemd-resolved 的一个功能，默认情况下是启用的（yes）。
  2. 当启用时，systemd-resolved 会在本地 127.0.0.53 地址上运行一个 DNS 存根监听器。
  3. 这个存根监听器会接收本地应用程序的 DNS 查询请求，然后转发给实际的 DNS 服务器。
  4. 当设置 DNSStubListener=no 时：
    • 存根监听器被禁用。
    • 本地应用程序的 DNS 查询将直接发送到配置的 DNS 服务器，而不经过 systemd-resolved

现在 tcpdump 虽然不卡了，但是抓包的时候通过 strace 看到还是会走 DNS 解析流程，这个时候的 DNS 解析都发给了 192.168.104.2:53 (配置在 /etc/resolv.conf 中)，也就是 systemd-resolved 的 127.0.0.53:53 udp 端口虽然在监听，但是不响应任何查询导致了超时，而 192.168.104.2:53 服务正常

补充：反向解析的调用链

前面一直在说”tcpdump 去做 DNS 解析”，这条链具体长什么样，画出来就清楚了。它和普通程序解析域名走的是同一条 NSS 链，只是入口函数不同：正向（域名→IP）是 getaddrinfo()，反向（IP→域名）是 getnameinfo()。

[!TIP]

PTR：PTR 是 DNS 里的一个记录类型（DNS RR type），全称 Pointer Record（指针记录），值 12，定义在 RFC 1035 §3.3.12

PTR 1.104.168.192.in-addr.arpa

内网私网段通常没有 in-addr.arpa 的授权 zone，所以 PTR 查不到，只能等超时——这就是抓包卡顿的直接原因

顺带区分几个容易混的：

几个可以从这张图直接读出来的结论：

  • /etc/hosts 能治：tcpdump 走的是 files 模块，和 ping/curl 同一条路。所以往 hosts 里写一条，PTR 根本不发。这跟 nslookup/dig 不读 hosts 正好相反——BIND 的三个工具绕开了整条 NSS 链，而 tcpdump 走的是它。
  • 5 秒从哪来：不是 tcpdump 的，是 glibc 的 RES_TIMEOUT=5、RES_DFLRETRY=2。resolv.conf 里不写 options timeout: 就是这两个值。
  • 内网几乎必然踩坑：私网段一般没有 in-addr.arpa 反解区，转发出去也是空的，查一次白等一次。正确处置是”别让它查”，不是”去修 DNS”。

验证它确实读 hosts，strace 一看就有：

看到 nss_files.so.2 + /etc/hosts ⇒ hosts 会参与解析（tcpdump 的实际情况）；只有 /etc/resolv.conf ⇒ 纯 DNS 客户端（dig 的情况）。

小结

其实很多应用中会偶尔卡顿，网络操作超时就是典型的导致这种卡顿的原因，从 CPU 资源使用率上还发现不了。比如日常 ssh 连服务器有时候就会卡 30 秒

关于 GSSAPIAuthentication 解释如下，一看也是需要走网络进行授权认证，如果没有配置 kerberos 服务就会卡在网络等待上：

[!TIP]

SSH 中的 GSSAPIAuthentication（Generic Security Services Application Program Interface Authentication）是一种身份验证机制，主要用于实现单点登录（Single Sign-On, SSO）功能。它允许用户在已经通过 Kerberos 认证的环境中，无需再次输入密码就可以登录到支持 GSSAPI 的 SSH 服务器。

修法优先级

同一个症状，按代价从小到大排：

优先级 做法 影响面 说明
1 tcpdump -n 只影响这一次抓包 完全关掉名字解析，数字形式打印 IP/端口。默认就该带
2 tcpdump -w out.pcap 只影响这一次抓包 落盘时格式是二进制的，没有名字解析这一步，完全不受 DNS 影响；事后 tcpdump -nr out.pcap 或 Wireshark 离线看，慢也慢在事后
3 /etc/hosts 写正确的名字映射 本机所有程序 只对写进去的那几个 IP 有效，换个对端照样卡。不要写成 192.168.104.4 localhost，会把这个 IP 在输出里全打印成 localhost
4 DNSStubListener=no + 重启 resolved 全机 本末倒置。所有本地应用失去 resolved 的缓存、按接口分流、DNSSEC、LLMNR；有容器依赖 127.0.0.53 会直接断。只解决了 tcpdump，没解决 resolved 本身为什么不答

前两条是抓包场景的标准做法，第三条是临时缓解，第四条不该作为解决方案——它是把问题挪走，不是修掉。

抓包机自身的副作用

反查不只是拖慢输出，它会让抓包机自己产生流量，这点在排查 DNS 问题时特别容易把人带偏：

  • 每抓到一个没见过的 IP，tcpdump 就打一次 PTR。一次几百个源地址的抓包，就是几百次 DNS 查询——这些查询混在同一段时间的 DNS 日志和抓包里，如果当时正在排查 DNS 或做流量分析，会被当成”意外的查询来源”。
  • 反查走的是抓包机自己的 /etc/resolv.conf。如果抓包机所在机器的 DNS 是坏的，抓包机自己是排查对象，这时它一边抓一边发 PTR，日志里看到的查询来源就是它自己，很容易误判成”有程序在异常解析”。
  • 用 -w 落盘的抓包没有这个问题（文件名就是 IP），所以事后分析一律推荐离线看 pcap，不要在下发流量的机器上边抓边解析。

所以 -n 不只是性能开关，也是隔离观测者与被观测对象的开关。抓包机要尽量”隐形”——不发多余查询、不产生额外流量，否则你观测到的现象里就掺了自己的干扰。

类似的网络卡顿/DNS 解析卡顿是很常见的，大家掌握好 Debug 手段。
