nslookup-OK-but-ping-fail

发表于 2019-01-09 更新于 2026-11-08 分类于 DNS 阅读次数：

nslookup 域名结果正确，但是 ping 域名 返回 unknown host

原文写于 2019-01，记录 2018 年两次线上定位。
2026-11 在 Rocky 8.10（glibc 2.28 / BIND 9.11.36 / dnsmasq 2.89）上把全文的结论重做了一遍实测。

结论：原文的机制分析是准的，尤其是「nslookup 不读 /etc/hosts、不看 nsswitch.conf」这一核心判断，实测完全成立。
需要修正的只有一处（原文第 76 行”查不到域名就换下一台 nameserver”），其余是版本演进（rotate 的实现变了）和这几年的新情况（dnsmasq hostsdir、nscd 从 RHEL 8 移除、dig 补 search 域的坑）。
详见第三章「2026 复核」。

TL;DR

同一台机器上，nslookup 能解析而 ping 不能，只有三种可能：走了不同的解析路径、用了不同的 nameserver、被本地缓存/本地数据源盖住了。

现象 最可能的原因 一句话验证
nslookup 有结果，ping/getent 没有 nslookup 不读 /etc/hosts、不看 nsswitch.conf，走的是纯 DNS strace -e trace=openat -f ping xxx 看它有没有打开 /etc/hosts
同上，且 getent 也没有 第一台 nameserver 对它返回 NXDOMAIN（NXDOMAIN 不换服务器） 对第一台单独 dig，看 rcode
同上，且 dig 和 nslookup 结果不一致 只在 /etc/hosts 或 dnsmasq 本地数据里有，DNS 上没有 dig @第一台 与 getent 对比
改完记录，dig 已经是新 IP，程序还是旧的 nscd（固定 TTL）／JVM 缓存／连接池／dnsmasq 内存里的 hosts 快照 逐层清：nscd -i hosts → 重启进程 → reload dnsmasq

一、问题的本质：三条不同的解析路径

这是整个问题的地基。nslookup、dig、host 是 BIND 带的自检工具，它们不是应用；而 ping、curl、ssh、数据库客户端、JVM 走的都是 C 库的解析入口。

实测证据（strace -f -e trace=openat，同一台机器查同一个名字）：

这正是原文总结里那句「nslookup 不会检查 /etc/hosts、/etc/nsswitch.conf，而是直接从 /etc/resolv.conf 中取 nameserver」——2026 年重做一遍，一字不差。

推论：/etc/hosts 里写死一条记录，本机程序会用这条，nslookup 完全看不到。这类”两边对不上”不是 DNS 坏了，是根本没问同一处。

实测补充（glibc 2.28）：/etc/hosts 命中之后，getent ahosts / getent ahostsv4 / ping / curl 一条 DNS 查询都不发，服务端日志和 strace 都确认了。所以 /etc/hosts 里一条过期的记录，能长期静默覆盖 DNS 的正确结果，而 dig 永远显示正确 —— 比 dnsmasq 的坑更深。

getent ahosts 在 /etc/hosts 命中、但 DNS 上有不同地址时，返回的只有 hosts 里那条。只有老的 getent hosts（走 gethostbyname2）在拿到 hosts 里的 IPv4 之后还会补发 AAAA 查询——这只影响它会多等一次超时，返回地址仍以 hosts 为准。

顺带纠正一个函数名

原文通篇说”ping 最终调 gethostbyname()“——注释里也标了”gethostbyname() 函数流程”。这在 2019 年就已经不准确了：现代 glibc 的 ping 用的是 getaddrinfo()（上面 strace 里出现 nss_dns.so.2 且要处理 A/AAAA 就是这个原因）。

原文第 83 段其实自己也写了”很多系统都已废弃 gethostbyname，使用 getaddrinfo 代替”，只是前半段的标题和结论没同步改过来。

结论不受影响：两个函数都走 NSS 链路。但如果你要去读代码、抓栈，函数名错了会找错地方。

二、当年那两台机器到底出了什么事

先记 Google 到的几类通用原因（这几条放今天依然成立）：

  • 名字末尾没加点，被自动追加了 search 域
  • resolv.conf 里的 nameserver 有不通的
  • nsswitch.conf 被写成 hosts: files mdns dns，而 DNS 服务器不答 mDNS
  • 单标签名字（如 db01）在 Windows 上走 NBNS 而不是 DNS（未复核，与 Linux 无关）

当年的环境是”两台 nameserver，第一台管内网，第二台管外网”。现象是 ping 把内网域名的查询丢给了第二台，自然解析不到。抓包确认：

第一层：resolv.conf 里的 rotate

出问题的都是新申请的一批机器，对比发现这些机器的 /etc/resolv.conf 多了 options rotate。去掉之后恢复。

当年的解释引用了 RHEL 的一个 solution：开着 rotate 时，glibc 把第一个 nameserver 挪到最后，于是”总是用第二个”。

第二层：nscd 缓存了错误结果

治了 rotate 之后还剩一台不通，抓包看它连查询都没发出去。strace 发现 ping 在访问 nscd 的 socket，返回值是 0（正常机器是 -1）；杀掉 nscd、删掉 /var/run/nscd/ 之后正常。

成因很典型：先为了排查 DNS 把 nscd 拉起来，nscd 把当时错误的结果缓存住了，导致后面改配置也不生效。

这两段的 2026 版结论

原文说法 复核结果
rotate 下”第二个总排第一” 老 glibc 上成立（2.17 的代码就是把队头挪到队尾，见 4.2 源码）。glibc 2.28 重写为进程内轮转 + 跨进程随机起点
nscd 缓存 DNS 结果 成立，且缓存时长不看 DNS TTL，由 /etc/nscd.conf 的 positive-time-to-live 决定（hosts 默认 3600s）
nscd 是 glibc 组件 成立，但 RHEL/CentOS 8 起已不再提供 nscd，CentOS 6/7 才是它的主要阵地
清缓存方式 nscd -i hosts 即可，不必删目录

三、2026 复核：哪些仍然成立，哪些要改

验证环境：Rocky 8.10 / glibc 2.28-251.el8 / BIND 9.11.36 / dnsmasq 2.89，用网络命名空间起多个独立 DNS 实例观察真实 qname。原始脚本与日志见文末。

原文结论 2026 复核
nslookup/dig 不读 /etc/hosts、不看 nsswitch.conf 成立，strace 实测一字不差
多个 nameserver 默认用第一个 成立
「查不到域名就换后面的 nameserver」 不成立，NXDOMAIN 不换。见 3.3
rotate 下”第二个总排第一” 老 glibc 成立，2.28 已重写。见 4.2
search 最多 6 个 原文自己的注里就标了 RHEL7 已修，2.28 实测 40 个全用上。见 3.4
nscd 会缓存、且会缓存错误结果 成立，且缓存时长不看 TTL
bind 工具只问第一台 成立，rotate 下也不轮转。见 3.2

下面按重要性展开新发现的和要改的。

1. dig 默认会补 search 域 —— 原文提到过，但容易被低估

原文在 Google 到的原因里列了「域名最后没有加点，被自动追加了 search 域」，这一条是对的，而且是最高频的坑。我用 dig 亲自撞了一次：

dig 9.11 默认就带 +search。想按原样发：

注意加尾点比 +nosearch 更保险：尾点还能防止名字里混入 search 域，在写脚本时尤其重要（我自己的第一版验证脚本就是全部查询都被补全成 xxx.db.tiger.internal 而全部落空）。

对 nslookup、host 也一样，三者都会按 search + ndots 补全。这是排查时最容易自我欺骗的一步：你查 db01，看到的答案其实是 db01.example.internal 的，然后拿这个结论去解释应用的失败，方向就错了。

2. dig/nslookup 不认 rotate —— 用它们判断”服务器选择”会误判

这一条原文没写，但它放大了原文那个 bug 的隐蔽性。三个 nameserver 都能答同一批名字，options rotate 下各查 12 次：

工具 ns1 ns2 ns3
getent ahosts（走 glibc） 4 4 4
dig 12 0 0
nslookup 12 0 0
host 12 0 0

glibc 会轮转，BIND 的三个工具永远只问第一台。所以：

  • 用 dig 验证”rotate 是否生效”→ 永远看不出效果
  • 用 dig 验证”第二台是否可用”→ 必须显式 @第二台
  • 生产上开了 rotate 之后，dig 能通不代表 ping 能通，反过来也一样

原文当年是用抓包（tcpdump port 53）发现查询落到了第二台的，没用 dig 去验证——这一点做对了。如果当时用 dig 判断，会得出完全相反的结论。

3. NXDOMAIN 不会触发换 nameserver —— 原文这里需要修正

原文第 76 行写：

如果 /etc/resolv.conf 中配置了多个 nameserver，默认使用第一个，只有第一个失败【如53端口不响应、查不到域名后再用后面的nameserver顶上】

前半句对（默认用第一个），括号里的内容把两种完全不同的情况混在了一起。实测（第一台用 Python 起了个可控应答器，第二台是正常 DNS）：

第一台的应答 是否改问第二台 getent 结果
超时（不响应） 是 成功
REFUSED 是 成功
SERVFAIL 是 成功
NXDOMAIN 否 失败
NOERROR 但无记录 否 失败

原因在 glibc 2.28 的 resolv/res_send.c 里写得很直白——send_dg 只在三种 rcode 上跳去问下一台，再加上一个特殊情况：

列表里没有 NXDOMAIN。 NXDOMAIN 拿到就原地返回。所以”查不到域名”（NXDOMAIN）不会让 glibc 去问下一台，”服务器坏了／拒绝服务／给个空壳应答”才会。

（超时不在这段里：它是 send_dg 内重发耗尽后 return 0，上层 goto next_ns。）

这条在排障上的意义：如果第一台 DNS 对某域名返回 NXDOMAIN（比如它没配这个 zone 的转发，直接把”不存在”甩给你），后面两台再正确也没用，而且抓包里看不到任何”尝试了第二台”的痕迹。这时 nslookup 域名 第二台 是通的——又一个”nslookup 正常、ping 不通”。

至于原文那台机器的实际成因，它的现象是查询被发给了第二台（抓包可见），说明不是 NXDOMAIN 挡路（NXDOMAIN 的话根本不会有第二个包）。真正的原因是 rotate 改变了起始服务器，第二台对内网域名答不上来就被放弃了。两件事在原文里写在了一句描述里，但原文的结论（”挑选的 nameserver 不对”）是对的。

4. search 域数量：原文连自己都标了”已在 RHEL7 修复”

原文写「search 只能支持最多 6 个后缀（代码中写死了）」，但同一段的引用里就写着 resolved in RHEL7 glibc package versions at or exceeding glibc-2.17-222.el7。也就是说这条在写文章的 2019 年就已经不是问题了，只是标题保留了这个说法。

在 glibc 2.28 上实测：

一个不漏，全部试完。代价是：每次解析最多 41 个查询、乘上 attempts 和每台的超时。 一个配错 search 的域名，能把一次解析拖到几十秒 —— 这比”只能 6 个”更值得记住。

5. 新的缓存层：Java 的 JVM 缓存

原文只讲到 nscd，因为当年是 C/C++ 应用为主。今天还多一层：JVM 在进程内自带 DNS 缓存，过期时间完全不参考 DNS 应答的 TTL，由 networkaddress.cache.ttl 决定（默认 30s，配成 -1 就是永久）。

这层不在本文范围，但排障时要知道：DNS 改完、nscd 清完，Java 应用还是连老 IP，那是 JVM 的事，跟 DNS 无关。

四、nameserver 的选择逻辑（实测版）

4.1 只有前 3 台生效

实测：前三台全死、第四台正常 → 解析失败（49ms，直接放弃）；前两台死、第三台正常 → 成功（47ms）；把能用的那台挪到第三位 → 成功。所以把 DNS 排在第四位是纯粹的安慰剂。

附带一条：三行都写同一个 IP，等于占掉三个槽位（实测确认——第 4 台确实被忽略）。配错了 DNS 地址在 resolv.conf 里复制粘贴，会把唯一的可用服务器挤出前三。

4.2 rotate 到底怎么转

这一条我看了源码。glibc 2.28 的 resolv/res_send.c 挑起始服务器是这么算的：

翻译成人话：

  • global_offset 是进程内静态变量，兜了一圈之后每次调用返回的偏移量恰好 +1，所以同一进程里的连续解析会依次落在 n, n+1, n+2, ... 循环 —— 这就是实测到的进程内严格轮转（下面贴了 raw 输出）。
  • 跨进程的起点是随机的（用 tv_sec ^ tv_usec 播种）。所以新起的进程第一次可能从任何一台开始。
  • 只有一台时不轮转（nscount <= 1 直接 return 0）。

实测三个独立进程、每个连续查 9 次（地址是各实例返回的固定值，10.9.1.x / .2.x / .3.x 分别对应 ns1/2/3）：

进程内严格循环、跨进程起点不定，跟源码一致。

4.2.1 老版本不是这样

glibc 2.17（CentOS 7 时代）的 res_send.c 是把队头挪到队尾：

顺序是原地轮转，而不是按时间偏移挑起点。

所以原文那句「rotate 下第一个 nameserver 总被挪到最后、于是实际总用第二个」——在 glibc 2.17 上是对的（这篇文章写于 2019，当年的机器多半是 CentOS 7），在 glibc 2.28 上是错的。

我确认的只是这两个版本各自的行为（2.17 旧、2.28 新）。精确的分界版本我没有逐个 tag 回归，只记得是 2017 年前后因 bug 19570 重写、大约在 2.26 附近，这句按「大约」理解，别当结论。

BIND 的三个工具不参与（见 3.2）—— 无论 glibc 新旧，它们永远是第一台。

这对排查意味着：同一个域名，ping 一次可能是 A 答的，下一次可能是 B 答的。复现不稳定本身就是 rotate 的特征。

4.3 attempts 与超时的代价

最坏情况 ≈ timeout × attempts × nameserver 台数，再乘以 qname 的尝试次数（本名 + search 域）。三台都超时、2 个 search 域、attempts:3，就是 2 × 3 × 3 × 3 = 54 秒。实际会按服务器的 index 做退避计算，不是简单相乘，但量级如此。

排查”为什么建连慢”时，先看 /etc/resolv.conf 里有没有已下线的 nameserver。

五、search 域与 ndots

5.1 顺序由 ndots 决定

实测（真机 glibc 2.28，服务端抓到的 qname 顺序）：

默认 ndots:1，所以带点的名字通常先按原样查；单标签名会先去撞 search 列表。

5.2 没有 search 行时，用 hostname 的后缀

实测：resolv.conf 里没有 search 时，主机名是 vm004.gzjf.db.tiger，查 nosrch.zz 实际发出的是 nosrch.zz 和 nosrch.zz.gzjf.db.tiger 两个。

这条在容器里经常变成惊喜：容器 hostname 是随机串，search 也没配，行为和宿主机完全不同。

5.3 A 和 AAAA 会都发出来

实测查一个名字，服务端会先后收到 query[A] 和 query[AAAA]（同一次解析里两个都发）。

至于二者是否真正并发（共用一个 socket、不等第一个返回就发第二个），我的日志只有秒级时间戳、分辨率不足以判定先后，这一条属于未严格验证，只能说”两个都发了”。

延伸出去的那条 K8s 结论 —— 两个查询共用一个 socket、DNAT 到同一后端时五元组冲突、有一个要等 5 秒重试 —— 是既有结论，本轮没有在 K8s 网络里复现，引用时请注意前提。options single-request-reopen 的作用是为每个类型新开连接，就是用来避开这个冲突的。

5.4 名字长度/数量边界

实测 70 个字符的单标签名，glibc 直接返回失败，一个包都没发出去（DNS 规范单标签上限 63 字节）。所以”名字太长导致解析失败”不是网络问题，本地就挡掉了。

六、本地数据源与缓存：三层要分清

6.1 三者定位

位置 干什么 缓存时长
nscd glibc 内部（NSS 缓存层） 缓存 getpwnam/getpwuid/hosts 等查询结果，不发包 固定，nscd.conf（hosts 默认 3600s）
systemd-resolved 53 端口的 stub + NSS 模块 缓存 + 转发 + 按接口分流 + LLMNR/mDNS 跟随 DNS TTL
dnsmasq 53 端口的转发器 转发 + 缓存 + 本地静态数据 + 按域名分流 + DHCP/TFTP 跟随 TTL，有上下限

6.2 dnsmasq 的 hostsdir：这轮实测最大的坑

hostsdir=/path/dir 的作用是”读目录里的 hosts 文件，并且改文件自动生效“。它解决的是 dnsmasq 最经典的问题：/etc/hosts 和 addn-hosts 都只在启动/收 SIGHUP 时读一次，改了不生效还不报错。

但它不会让 /etc/hosts 自动重读。直接看内核视角的监控对象：

第一个是监视 resolv.conf 的父目录（注意只是目录，用于感知 resolv.conf 变化），跟 hosts 无关。我专门验证过：在这个配置下改 /etc/hosts，read /etc/hosts 的计数纹丝不动，查询继续 NXDOMAIN，直到发一个 SIGHUP。

追加一行到已有文件 自动生效
sed -i 原地改（换 inode） 自动生效
删掉文件里的一行 自动生效，该记录消失
删掉整个文件 自动生效，记录消失
mv 换入新文件 自动生效
改 /etc/hosts 完全不生效
子目录里的文件 不读，日志里连事件都没有
点开头的文件 .hidden 不读，静默
非 hosts 格式文件 照样按 hosts 解析，非法行报 bad address 后继续读下一行
目录在启动时不存在 只打一行警告，服务照常起；之后建目录也没用，不会补挂 watch
目录权限 000 且 user= 降权 failed to create inotify: Permission denied，也不会生效
同名记录（hostsdir vs /etc/hosts） 两条都返回，不是覆盖
同一目录两个文件同名 两条都返回，顺序随最后重载的文件变，别靠字母序做优先级
address= 与 hosts 文件（含 hostsdir、addn-hosts）同名 hosts 文件赢，address= 被盖住

TTL 方面：hosts 来源的答案走 local-ttl，未配置时为 0。这是识别”答案来自本地数据而不是转发”的唯一可靠指纹 —— 比 aa/ra 可靠得多。

对照组：addn-hosts=/path/dir 也接受目录、也按字母序读，但 strace 里一个 inotify_add_watch 都没有，改文件必须 SIGHUP。hostsdir 才是唯一会自动重载的写法。

6.4 容器

Docker 会把宿主 resolv.conf 里的 loopback 地址（127.0.0.1）过滤掉；过滤后为空时默认用 8.8.8.8/8.8.4.4。所以宿主机上跑的 dnsmasq 对容器默认是透明的，容器解析结果和宿主不一致是常态，不是故障。要修得在 daemon.json 里显式配非 loopback 的 DNS。

八、总结

  1. 路径不同是根因的大头。 ping/curl/getent 走 glibc + nsswitch（先 /etc/hosts），nslookup/dig/host 直接发 DNS 报文。strace 一看就分开。
  2. 名字可能被改写。 四类工具都会按 search + ndots 补全，但机制不同：BIND 三个工具自己做补全（dig 默认 +search）；ping/curl/getent 是 glibc 做的。写脚本时一律用尾点 FQDN。
  3. NXDOMAIN 不换服务器，REFUSED/SERVFAIL/超时才换。 第一台返回”不存在”，后面的服务器再对也没用。
  4. 只有前 3 台 nameserver 生效。
  5. rotate 只有 glibc 认，BIND 工具不认。 进程内轮转，跨进程起点不定。用 dig 验 rotate 永远验不出来。
  6. 本地数据源最容易骗人。 /etc/hosts（files 命中后不再查 DNS）、dnsmasq 的 hosts 快照、nscd 的固定时长缓存、systemd-resolved 的副本，四者机制不同，现象都是”改了不生效”。
  7. dnsmasq 的 hostsdir 只管那个目录。 它不会让 /etc/hosts 自动重读；目录必须启动时就存在，否则只留一行警告、之后也不会补。
  8. 没有源码时，strace + 抓包能看清一切；有测试机时，别靠推理下结论。
